## 1. Назначение системы

Серверная часть многопользовательской карточной игры. Игроки подключаются с
клиента на Unity, садятся за столы и играют в No-Limit Texas Hold'em в формате
кэш-игры. Число столов не ограничено, за каждым столом до 6 игроков.

Клиент **тонкий**: он не реализует правил игры, не хранит колоду и не имеет
доступа к картам соперников. Вся игровая логика, все карты и все фишки
находятся на сервере. Клиент отображает то, что прислал сервер, и передаёт
действия игрока.

Это не только вопрос архитектуры, но и вопрос защиты: в клиентской логике
покера любую проверку можно обойти модификацией приложения.

## 2. Термины

| Термин | Значение |
|---|---|
| **Стол** | игровая единица на 6 мест с фиксированным уровнем ставок |
| **Место (seat)** | позиция за столом, 0–5; принадлежит игроку, пока он не встал |
| **Раздача (hand)** | одна партия от постановки блайндов до распределения банка |
| **Улица (street)** | этап раздачи: префлоп, флоп, тёрн, ривер |
| **Баттон** | позиция дилера, сдвигается на каждой раздаче |
| **Блайнды** | обязательные ставки: малый (SB) и большой (BB) |
| **Стек** | фишки игрока за столом |
| **Баланс** | фишки игрока вне стола, «кошелёк» |
| **Бай-ин** | сумма, с которой игрок садится за стол |
| **Банк (pot)** | разыгрываемые фишки |
| **Сайд-пот** | дополнительный банк при олл-ине игрока с меньшим стеком |
| **Сит-аут** | игрок за столом, но не участвует в раздачах |
| **Автоподбор** | сервер сам выбирает стол со свободным местом |

## 3. Роли

**Игрок (гость).** На этом этапе аутентификация — заглушка: игрок вводит ник и
получает гостевой аккаунт со стартовым балансом. Может: подобрать стол, играть,
докупать фишки, выходить в сит-аут, вставать из-за стола.

**Администратор / разработчик.** Доступ к служебным HTTP-эндпоинтам:
состояние сервера, список столов, контрольные суммы колод.

Роли модератора, поддержки и кассы в первом этапе не предусмотрены.

## 4. Функциональные требования

### 4.1. Аутентификация

| № | Требование |
|---|---|
| A1 | Игрок получает токен по нику через `POST /auth/guest`, без пароля |
| A2 | Токен действует 30 суток и служит ключом от аккаунта; клиент обязан сохранить его на устройстве |
| A3 | Продление личности выполняется предъявлением прошлого токена; передавать `player_id` напрямую запрещено — он публичен |
| A4 | Все игровые операции требуют валидного токена |
| A5 | Одному игроку соответствует одно активное соединение; новое вытесняет старое, место за столом сохраняется |

### 4.2. Подбор стола

| № | Требование |
|---|---|
| B1 | Игрок выбирает уровень ставок; сервер сам находит стол со свободным местом |
| B2 | Если подходящего стола нет, создаётся новый |
| B3 | При наличии нескольких подходящих выбирается самый заполненный |
| B4 | Одновременно игрок может сидеть только за одним столом |
| B5 | Бай-ин ограничен минимумом и максимумом уровня ставок и списывается с баланса |
| B6 | Пустой стол удаляется через заданное время |

### 4.3. Правила игры

Реализуется No-Limit Texas Hold'em, кэш-игра, до 6 участников.

| № | Требование |
|---|---|
| C1 | Раздача начинается при наличии минимум двух готовых игроков |
| C2 | Баттон сдвигается на следующее занятое место каждую раздачу |
| C3 | Блайнды: SB слева от баттона, BB следом; в хедз-апе баттон ставит SB |
| C4 | Игрок, которому не хватает на блайнд, ставит всё и уходит в олл-ин |
| C5 | Каждому раздаётся 2 закрытые карты; карты видит только владелец |
| C6 | Четыре круга торговли: префлоп, флоп (3 карты), тёрн (1), ривер (1) |
| C7 | Порядок хода: префлоп — первый после BB (в хедз-апе баттон), постфлоп — первый живой слева от баттона (в хедз-апе BB) |
| C8 | Большой блайнд получает право хода после лимпов |
| C9 | Действия: фолд, чек, колл, бет, рейз, олл-ин |
| C10 | Минимальный рейз равен предыдущему повышению, но не меньше BB; растёт по ходу торговли |
| C11 | Неполный олл-ин не открывает круг торговли заново: сходившие игроки могут только уравнять или сбросить, в том числе через олл-ин |
| C12 | Повышение недоступно, если ни у одного соперника не осталось фишек |
| C13 | При олл-инах формируются сайд-поты по уровням вкладов |
| C14 | Неколированный излишек ставки возвращается игроку до вскрытия |
| C15 | При равных руках банк делится; нечётные фишки — первому слева от баттона |
| C16 | Если торговаться некому, оставшиеся улицы открываются автоматически |
| C17 | Если остался один неспасовавший игрок, карты не вскрываются |
| C18 | Все суммы — целые фишки |

**Инварианты, обязательные к соблюдению:**

* сумма фишек за столом не меняется в течение раздачи;
* одна и та же карта не может быть выдана дважды;
* стек не может стать отрицательным;
* каждая раздача завершается за конечное число действий.

### 4.4. Таймеры и отсутствие игрока

| № | Требование |
|---|---|
| D1 | На решение даётся ограниченное время (по умолчанию 20 с) |
| D2 | Отключённому игроку время увеличивается на льготный период |
| D3 | По истечении сервер ходит сам: чек, если возможен, иначе фолд |
| D4 | После заданного числа авто-фолдов подряд игрок переводится в сит-аут |
| D5 | Клиенту передаётся абсолютный серверный дедлайн, чтобы не зависеть от локальных часов |

### 4.5. Реконнект

| № | Требование |
|---|---|
| E1 | Место сохраняется за отключившимся игроком заданное время (по умолчанию 120 с) |
| E2 | Раздача не приостанавливается: очередь отключённого закрывается авто-фолдом |
| E3 | При возврате игрок получает полный снимок стола, включая свои карты, борд, банк и остаток времени на ход |
| E4 | Если игрок не вернулся, место освобождается, стек возвращается на баланс |

### 4.6. Управление местом

| № | Требование |
|---|---|
| F1 | Игрок может выйти в сит-аут и вернуться в игру |
| F2 | Игрок может докупить фишек с баланса в пределах максимального бай-ина |
| F3 | Докупка во время раздачи вступает в силу со следующей |
| F4 | Сит-аут, поставленный сервером (нулевой стек, серия авто-фолдов), снимается докупкой автоматически |
| F5 | Выход во время раздачи откладывается до её окончания |
| F6 | При выходе стек возвращается на баланс |

### 4.7. Честность раздачи

| № | Требование |
|---|---|
| G1 | Во время игры случайные числа не генерируются |
| G2 | Используется заранее подготовленный набор перемешанных колод (на первом этапе — 10) |
| G3 | Колоды выдаются последовательно по глобальному счётчику, общему для всех столов и инстансов |
| G4 | Набор колод расширяется без изменения кода |
| G5 | Каждая раздача помечается идентификатором колоды и номером выдачи для последующей проверки |
| G6 | Карты колод не отдаются через API до окончания раздачи |

## 5. Нефункциональные требования

| Категория | Требование |
|---|---|
| **Протокол** | Один WebSocket на игрока; JSON в текстовых фреймах; HTTP только для получения токена и служебных запросов |
| **Согласованность** | Состояние стола изменяется последовательно; гонки между ходом игрока и срабатыванием таймера исключены на уровне архитектуры |
| **Отказоустойчивость** | Ошибка в одной раздаче не останавливает стол; ни один клиент не должен зависать в ожидании ответа |
| **Деградация** | При недоступности Postgres и Redis сервер продолжает работу с предупреждением в логе |
| **Защита от злоупотреблений** | Ограничение частоты сообщений от клиента; некорректные сообщения не разрывают соединение |
| **Конфигурируемость** | Уровни ставок, таймеры, размеры стола и окна реконнекта задаются переменными окружения |
| **Развёртывание** | Полный стенд поднимается одной командой `docker compose up` |
| **Тестируемость** | Игровые правила покрыты тестами без запуска сервера |
| **Логирование** | Ключевые события стола (старт раздачи, посадка, таймаут, ошибка) пишутся в лог с идентификаторами стола и раздачи |

## 6. Границы первого этапа

### Входит

* WebSocket-сервер и протокол обмена
* Полные правила NL Texas Hold'em, 6-max, кэш
* Автоподбор стола, три уровня ставок
* Гостевая авторизация
* Заранее подготовленные колоды с последовательной выдачей
* Таймеры хода и авто-фолд
* Реконнект с восстановлением состояния
* Сит-аут, докупка, выход
* PostgreSQL и Redis, Docker Compose
* Тесты игровых правил
* Утилита для прогона ботов

### Не входит

| Не входит | Комментарий |
|---|---|
| Регистрация с паролем, восстановление доступа | заглушка спроектирована под замену без переделки остального |
| Турниры (SNG, MTT) | ядро к этому готово, требуется надстройка над столом |
| Другие варианты покера (Omaha и прочие) | требуется отдельная оценка комбинаций |
| Рейк | точка вставки определена |
| Чат за столом | протокол предусмотрен, в объём этапа не входит |
| История раздач в интерфейсе | запись в БД реализована, включается флагом |
| Работа нескольких инстансов сервера | столы живут в памяти процесса |
| Криптостойкая генерация колод, commit-reveal | сознательное ограничение этапа, см. раздел 8 |
| Античит, детект сговора | — |
| Платежи, вывод средств | — |
| Клиент на Unity | предмет отдельных работ |

## 7. Критерии приёмки

Этап считается принятым, если выполняется всё перечисленное.

1. `docker compose up --build` поднимает сервер, Postgres и Redis; `GET /health`
   отвечает `status: ok`.
2. Шесть ботов (`scripts/bot_client.py --bots 6 --hands 20`) садятся за один
   стол через автоподбор и играют 20 раздач без ошибок в логе.
3. Все тесты проходят: `pytest` либо `python tests/run_all.py`.
4. Марафон раздач подтверждает инварианты раздела 4.3 на каждой раздаче.
5. Обрыв соединения игрока и переподключение в течение окна возвращают его на
   то же место с корректным состоянием.
6. Отсутствие реакции игрока приводит к авто-ходу в отведённое время, стол
   продолжает раздавать.
7. Десять последовательных раздач используют десять разных колод; одиннадцатая
   повторяет первую.
8. Расширение набора колод до 100 выполняется одной командой и не требует
   изменений в коде.
9. Документация соответствует реализации: протокол, архитектура, инструкция
   для клиента.

## 8. Известные ограничения

Перечислено явно, чтобы не считалось недоработкой.

**Фиксированный набор колод.** Воспроизводимость получена ценой
предсказуемости: игрок, увидевший 10 раздач, знает все возможные колоды, а зная
позицию счётчика, предскажет следующую. Для игры на условные фишки это
приемлемо, для игры на деньги — нет. Требуется криптостойкий шафл на раздачу и
схема commit-reveal. Точка расширения локализована в одном методе.

**Гостевая авторизация.** Аккаунт привязан к токену на устройстве. Потеря
токена означает потерю баланса; переноса между устройствами нет.

**Один инстанс сервера.** Состояние столов хранится в памяти процесса.
Перезапуск сервера прерывает идущие раздачи: стеки игроков за столами будут
потеряны, так как они не персистятся до конца раздачи.

**Ограничение на рост.** Каждый стол — отдельная асинхронная задача. Для сотен
столов на инстанс этого достаточно; для тысяч потребуется профилирование и,
вероятно, шардирование.
